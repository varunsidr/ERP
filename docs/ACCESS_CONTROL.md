# Access control

The app has five roles. Access is checked on the server for both page actions and REST API mutations; hiding a button is not the security boundary. All signed-in users can view the operational pages and analytics, including the CSV export.

| Role | Allowed changes |
| --- | --- |
| Admin | All changes, payment recording, and user creation |
| Sales | Customers, sales orders, and invoice issuance |
| Purchasing | Suppliers and purchase orders, except stock receipt |
| Inventory | Products, reasoned stock count corrections, manual stock additions, and purchase receipts |
| Staff | Read-only |

New users can open **Create an account** from the login page. Their account starts as **Pending**, with no access to operational pages or API data. They must confirm control of their email address before an Admin can approve them. Verification and password recovery links contain random, one-use tokens; only token hashes are stored, links expire after 30 minutes, and reset requests use the same response whether or not the email is registered. Resend and recovery requests are rate limited. An Admin opens **Users** in the sidebar, reviews verified requests, and assigns one of the five roles. Admin-created users are marked verified because an Admin provisions the account directly. Admins can also change roles for approved accounts and deactivate/reactivate accounts. Role changes and access changes revoke existing sessions; Admins cannot change their own role, deactivate their own account, or remove the last active Admin. Users can change their own password from **Account security** after confirming their current password. Existing API tokens and browser sessions are checked against the user's active flag and token version on each request. Deactivation, reactivation, approval, role changes, and password changes advance the token version so prior sessions stay revoked; pending users cannot retain access. Unknown role values fall back to Staff.

Admins can review recent, committed actions in **Activity log**. Account requests, approvals, role/access changes, master-record creation, stock changes (including reasoned count corrections), sales and purchase order transitions, invoices, and payments are written to the audit table in the same transaction as the business change. The log shows the latest 100 events. There is no application route to edit or delete events. This is an append-only application feature, not tamper-proof storage against database administrators.

Inventory users can record a partial purchase delivery from the purchase order page. Each receipt names purchase order lines and delivered quantities; the server locks the order, caps every line at its outstanding quantity, updates inventory and receipt history in one transaction, then marks the order partially or fully received. REST clients send `POST /api/purchase-orders/:id/receive` with an `Idempotency-Key` and an `items` array of `{ purchaseOrderItemId, quantity }`; the key is scoped to that purchase order and bound to the requested quantities. Omitting `items` receives all remaining quantities. Use a fresh key for each new delivery. Cancelling after a partial delivery closes the outstanding commitment while preserving already received stock and its history.

Browser forms use CSRF tokens tied to the session and an HTTP-only cookie. Session and CSRF cookies are `Secure` in staging and production; deploy behind HTTPS. The server requires an explicit `NODE_ENV` (`development`, `test`, `staging`, or `production`) before it starts, and an omitted environment cannot fall back to console mail. Staging and production startup require `MAIL_HOST`, `MAIL_PORT`, `MAIL_USER`, `MAIL_PASSWORD`, `MAIL_FROM`, and an HTTPS `PUBLIC_APP_URL`. SMTP requires TLS; use provider credentials intended for application mail and keep them in the deployment secret store. Development without SMTP prints one-use links to the local server console only. The app validates its PostgreSQL URLs, minimum JWT secret length, port, exact CORS origins, and `TRUST_PROXY_HOPS` before listening. Set proxy hops only to the number of trusted proxies in front of the app; leave it at `0` when clients connect directly. Responses include a content security policy, frame protection, and restricted browser permissions; HSTS is enabled in staging and production. API clients use Bearer tokens, not browser cookies. Keep `JWT_SECRET`, database credentials, and mail credentials out of Git.

Sign-in defaults to 10 attempts per client IP per 15 minutes across web and API routes; public signup defaults to 5 per IP per 15 minutes. `AUTH_LOGIN_ATTEMPT_LIMIT` and `AUTH_SIGNUP_ATTEMPT_LIMIT` may be set from 1 to 1000 for controlled environments; keep production values conservative and consistent across instances. An atomic PostgreSQL bucket store shares these limits across app instances. It stores an HMAC of the limiter purpose and client IP rather than the raw IP, and periodically removes expired buckets. Keep `JWT_SECRET` stable across instances so they calculate the same private client key.

For a hosted database, set `ERP_SEED_ADMIN_PASSWORD` to a unique password of at least 12 characters before running `npm run db:seed`. The seed only creates the Admin when missing; it **does not reset** an existing Admin password. The local-only default is for a database on localhost.

This is an access-control foundation, not a production security sign-off. Reviewed PostgreSQL-backed browser/API contracts cover primary role boundaries, signup verification, recovery, and session revocation; they do not exhaustively cover every page, mutation, or failure mode. Sales and Admin can issue invoice returns and credit notes; return transactions lock the invoice and support idempotent retries. Remaining before live business data: hosted backup retention, a staging restore rehearsal, deployment monitoring, and broader failure-recovery testing. The recovery procedure is documented in [the runbook](OPERATIONS_RECOVERY.md), but provider settings and cutover have not been rehearsed. CI performs a dump/restore integrity smoke against its disposable PostgreSQL service; it does not back up or restore hosted business data. The database rejects invalid stock quantities, nonpositive payments, invalid line quantities, and negative prices/totals. The core order, receipt, invoice, stock, payment, and return paths recheck state under PostgreSQL row locks. API payment, purchase receipt, and return clients can supply an `Idempotency-Key`; matching retries return the existing result, payment or receipt keys reused with different details are rejected, and a different key cannot repeat a completed receipt batch. Reviewed concurrency contracts cover the principal transitions, with broader end-to-end authorization and failure-recovery testing still needed.
